# A-D 阶段分析规则（唯一权威来源）

来源路径：`references/analysis-stages.md`。

本文件集中维护架构图的阶段 A、B、C、D 分析规则。SKILL.md 与命令行工作单只能引用或从这里生成，不得维护第二份规则正文。

时序图和端到端链路图不套用架构模块分层，但关系仍需证据并检查入口至终点的连通性。

架构分析按 A → B → C → D 顺序执行；阶段不完整或审计失败时不得渲染。

分析对象限定为 Python 软件项目，不限业务领域或 Python 框架。扫描器对项目做通用文件盘点，并对 Python 源文件生成 AST 结构事实；若 Python 源文件数为 0，停止语义分析与绘图。混合仓库只分析 Python 子系统；非 Python 文件仅作路径盘点，只有 Python 源码直接证明跨边界调用时才可记录外部端点，不分析对端内部结构。固定项目样本只用于回归，不作为命名、分层或架构模板。

#### 阶段 A：模块候选提取

- 结合 Python AST、依赖图、入口清单和关键 Python 文件逐段阅读，先细后粗，列出所有可能的架构组件：入口/路由、控制器、服务、Agent/任务执行器、状态机、工具、模型/协议适配器、仓储、数据源、文件/缓存、后台任务、配置注册、可靠性/治理机制及外部依赖。候选模块必须由 Python 源码职责支持；混合仓库的非 Python 文件不单独形成模块。
- 记录候选 ID、职责类型、暂定中文名、源码证据（路径、行号、该段证明什么）。对同文件中的不同职责、不同数据库/服务/协议、不同 Agent 与工具分别列候选，不提前合并。
- 记录盘点范围和跳过项。AST/索引结果和文件名只是定位线索；实现职责必须由 Python 源码内容确认。跨边界服务关系必须有 Python 代码中的 HTTP、消息、进程或数据访问证据。

#### 阶段 B：分层归类与模块定稿

- 按“主要职责”映射到通用职责层：接入、编排、能力、业务、数据与外部依赖、治理与可靠性。可按项目语义调整显示名称，但不得按行业模板强行套层；确实没有的角色写进 `absentRoles` 和理由，不创建空层或虚构组件。无法归类的候选显式放入待归类层并说明不确定点。
- 所有候选都必须且只能有一个处置结果：`included` 进入一个最终模块；`merged` 合入一个职责高度重叠且没有独立数据/协议/调用边界的模块，并写明原因；`excluded` 写明排除理由。最终模块须回指至少一个候选并有独立源码证据。
- 按单一职责与独立边界拆分。Agent、工具、领域对象、不同存储引擎、不同数据用途、独立外部服务优先分开；候选中出现多个动作/对象时复查，但不可仅按名称机械拆分。
- 先细后粗：阶段 A 宁可多列候选，阶段 B 再按源码证明的职责边界合并；不得为图面简洁而提前合并独立 Agent、工具、业务对象、协议、存储或数据用途。
- 主图模块总数硬范围为 12–25；若证据确实不足而少于 12，必须在 `densityReview.mainGraphException` 写明原因和证据。不得虚构模块补数，超过 25 时拆图，不得合并职责。
- 每层 3–5 个模块是排版目标，不是硬指标；少于 3 个或多于 5 个写入审阅警告并说明原因，不得为凑数合并真实职责。
- 最终主图模块逐个进行拆分信号自检：复核复合动作、状态与控制、调度与执行、技术/协议边界、数据用途、生命周期和独立关系。发现尚未拆开的独立职责时返回本阶段继续拆；若信号只是命名造成，必须用源码职责说明为何仍是单一模块。不得按固定目标密度牺牲真实边界。

#### 阶段 C：关系提取（逐模块、逐分支、逐副作用）

- 对最终模块逐个检查入边与出边；沿入口分别检查主分支、条件分支、并发/后台任务、异常/重试、终止/返回路径。重点追踪注册表与工厂、依赖注入、配置键到实现的映射、Agent 到工具执行器的真实调用、业务模块的写入/事件/外部调用副作用、数据读写和调用结果回传。
- 关系必须用显式字段表达：`from → to | kind | label | evidence[]`。`kind` 限于 `function_call`、`http`、`message`、`event`、`dependency_injection`、`configuration`、`data_read`、`data_write`、`file_read`、`file_write`、`external_call`、`model_call`、`process_spawn`、`retry`、`governance`、`import`、`other`。条件关系写 `condition`；区分“注册/允许调用”和“主运行路径确实会调用”。
- 有源码证据的关系不得因视觉重要性、主次或图面简洁而从完整关系清单中丢失。没有证据不画；将预期但未发现的关系写入 `notes.md`。一个关系对应多处实现证据时保留全部关键 evidence。

#### 阶段 D：主链路完整性校验

- 为每条主要成功路径明确入口、终点类型（回复、持久化、完成或移交）、顺序节点和关系 ID。确认每个相邻节点对都有同方向的阶段 C 关系，并沿有向边可达终点；不能只列节点序列而不提供边。
- 另外做候选清点、逐模块入边/出边清点、所有产生副作用的动作清点、路由/工厂/注册表映射清点、存储/外部调用与返回/终止清点。对每条关系、每个节点回到证据源码复核；检查图中是否出现没有关系清单支撑的边。
- 若主链路有断点或候选组件存在未解释的关键出边，回到阶段 C 补边，再重新执行 D，记录 `iterations` 与 `backfilledRelationIds`。仍无法确认时标记阻塞/待确认，禁止宣称完整。
- `coverageReview.moduleReviews` 必须为每个最终模块各写一条记录，逐项列出与阶段 C 完全一致的 `incomingRelationIds`、`outgoingRelationIds`，以及本模块的 `sideEffectRelationIds`；并确认 `branchesReviewed=true`。若源码中发现尚未建模的动作，将其写入 `unmodeledActions` 并返回阶段 C 补关系，不能带着未解释动作通过审计。没有入边/出边时明确写空数组。
- 所有阶段 C 关系都须由主图或某张子图边的 `relationIds` 覆盖；每条图边也须引用一个或多个阶段 C 关系。关系太密就拆图；不能只在分析清单里保留、却从可视输出中静默漏掉。
- 用 `architecture-diagram audit-analysis analysis.json diagram.json` 执行结构与有向连通性检查。该工具可验证候选处置覆盖、层/模块指向、证据字段与可选本地行号范围、每个图节点是否映射到阶段 B 的证据模块、每个阶段 B 模块是否出现在主图或子图、逐模块入边/出边清单是否与阶段 C 完全一致、未建模动作是否清零、每条关系是否映射到带方向一致端点的图边、主路径边序及入口可达终点。审计通过不等于模型已发现全部源码关系；最终仍需按本阶段的代码阅读清单人工回读。
